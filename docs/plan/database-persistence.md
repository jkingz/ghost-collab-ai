# Database Persistence Plan

## Objective

Move project metadata and project membership data from the editor's in-memory state into Supabase Postgres while keeping Clerk as the application's identity provider.

This slice covers project creation, listing, retrieval, renaming, deletion, ownership, and collaborator membership records. It does not persist the collaborative canvas or generated specifications yet; those remain planned for the Vercel Blob and background-task work described in the architecture context.

## Architectural decisions

- Clerk remains responsible for sign-in, sessions, and route protection.
- Supabase Auth is not used for the application's sign-in UI.
- The server creates a Supabase client with `@supabase/supabase-js` and passes the Clerk session token through the client's `accessToken` option.
- Clerk user IDs are stored as text values from the token `sub` claim.
- `projects` stores project ownership and metadata.
- `project_members` stores collaborator membership rows.
- Project IDs are UUIDs for internal relations; slugs are unique, user-facing identifiers.
- Row Level Security (RLS) is enabled on every exposed table.
- Owners can mutate their project metadata and memberships. Owners and collaborators can read projects they can access.
- Large generated artifacts are stored outside Postgres and referenced by database records in a later feature slice.

## Data model

### `public.projects`

| Column | Purpose |
| --- | --- |
| `id` | UUID primary key generated by Postgres |
| `owner_id` | Clerk user ID stored as text |
| `name` | Display name, trimmed and limited to 120 characters |
| `slug` | Unique lowercase URL-safe identifier |
| `created_at` | Creation timestamp |
| `updated_at` | Last metadata update timestamp |

### `public.project_members`

| Column | Purpose |
| --- | --- |
| `project_id` | Foreign key to `projects.id`, deleted with its project |
| `user_id` | Clerk collaborator user ID stored as text |
| `role` | Currently constrained to `collaborator` |
| `created_at` | Membership creation timestamp |

The composite primary key `(project_id, user_id)` prevents duplicate memberships. The user ID index supports membership lookups for the RLS access check.

## Implementation sequence

1. Create the Supabase project and configure its Data API.
2. Connect Clerk to Supabase as a Third-Party Auth provider.
3. Ensure Clerk session tokens include `role: authenticated`.
4. Add the Supabase URL and publishable key to the local environment.
5. Create the versioned migration files using the Supabase CLI.
6. Apply migrations locally and/or to the linked remote project.
7. Add the server Supabase client that forwards Clerk tokens.
8. Add a project service for validation, slug generation, CRUD operations, and error translation.
9. Add authenticated API routes for project operations.
10. Replace mock editor project state with API-backed state and refresh after mutations.
11. Verify RLS, API behavior, linting, and TypeScript compilation.

## Security requirements

- Never put a Supabase secret or service-role key in a `NEXT_PUBLIC_*` variable or client component.
- Do not use Clerk user metadata as an authorization source.
- Every mutation must be authenticated at the route boundary and constrained again by database RLS.
- The `UPDATE` policy must include both `USING` and `WITH CHECK`.
- Do not rely on `TO authenticated` alone; every policy also checks the relevant owner or membership relationship.
- Keep route handlers thin. Validation and persistence behavior belongs in the project service.
